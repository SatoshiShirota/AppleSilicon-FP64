# AppleSilicon-FP64

Apple SiliconのMetalで、FP64形式の実数密行列積を計算するライブラリーと実験用コマンドである。公開APIとコマンドはC、Metalの資源管理と実行指示はObjective-Cで実装する。C++からも同じCのヘッダーと関数を利用できる。尾崎スキームIIの整数剰余による行列積を使い、値に依存する演算をすべてGPUで実行する。

## 用語

| 用語 | この文書での意味 |
|---|---|
| 法 | 整数の余りを求めるときの除数。 |
| CRT | 中国剰余定理による復元。複数の法に対する余りから、範囲内の整数を一意に求める。 |
| 整数幅 | 行または列の最大値を基準として、整数化で残す二進数の桁数。FP64の仮数の桁数とは異なる。 |

## 計算の定義

入力は有限のFP64値を持つ、行優先の連続した行列$`A\in\mathbb{R}^{M\times K}`$と$`B\in\mathbb{R}^{K\times N}`$である。係数付きの積、転置、NaN、無限大の入力を含むBLAS互換の操作は扱わない。空の行列と$`K=0`$を許容する。

行列$`A`$の行ごとに$`h_i=1+\lfloor\log_2\max_k|A_{ik}|\rfloor`$、行列$`B`$の列ごとに同じ定義で$`g_j`$を決める。全要素がゼロの場合の指数は0とする。指数の取得にはFP64のビット列を使う。

整数幅を$`p_A,p_B`$とすると、計算する整数は次の式で定まる。$`\mathrm{trunc}`$はゼロ方向への切り捨てである。

$$
Q^A_{ik}=\mathrm{trunc}(A_{ik}2^{p_A-h_i}),\qquad
Q^B_{kj}=\mathrm{trunc}(B_{kj}2^{p_B-g_j})
$$

出力は整数行列積を復元した後、FP64形式へ最近接偶数丸めした値である。非正規化数は最終的な刻みに直接丸める。範囲を超える値は符号付きの無限大になる。厳密にゼロとなる積は正のゼロになる。負の値が丸めによってゼロになる場合は負のゼロになる。

$$
\widehat C_{ij}=\mathrm{RN}_{64}\left((Q^A Q^B)_{ij}2^{h_i+g_j-p_A-p_B}\right)
$$

この定義は、元の入力を無条件に損失なく保持する保証や、`cblas_dgemm`とのビット単位の一致を意味しない。たとえば$`A=[1,-1,2^{-80}]`$、$`B=[1,1,1]^T`$では、整数幅が60のときに小さい項が消える。必要な整数幅は入力の指数の分布と、許容する誤差によって決まる。

## GPUでの計算

GPUで使う演算を次の表に示す。

| 演算 | 実行の方法 |
|---|---|
| 行と列の指数の取得 | FP64のビット列から整数演算で求める。 |
| INT8の余りへの変換 | 仮数と指数から整数化した値の余りを求める。 |
| INT8入力・INT32蓄積による行列積 | Metalの`mpp::tensor_ops::matmul2d`を使う。 |
| CRTとFP64形式への丸め | 整数配列から結果のビット列を組み立てる。 |

法には256以下の互いに素な整数を大きい順に使う。合成数によって複数の素因数を一つの行列積で扱う。法の積$`P`$が$`P>2K2^{p_A+p_B}`$を満たすまで法を選ぶ。利用できる法の積では要求された整数幅を支えられない場合、計算を拒否する。整数幅を自動的に減らす処理は行わない。

余りは符号付きINT8に収める。内積は各部分の絶対値の総和が$`2^{24}`$以下になる長さに分割する。この範囲では、FP32の中間値を使う実行でも整数を正確に表せる。部分内積はINT32でまとめて加算し、オーバーフローしない長さごとに余りを求める。INT32の出力型だけを根拠に、長い内積全体の整数精度を仮定しない。整数化の指数は分割によって変えない。

CRTでは、各法について$`W_t=(P/m_t)((P/m_t)^{-1}\bmod m_t)`$を作成する。各出力の余りを$`r_t`$とすると、$`Y=\sum_t r_t W_t`$を基数$`2^{18}`$の整数配列で求める。各桁の積の総和と繰り上がりは32ビット符号なし整数に収まる。桁ごとの総和には、他の桁への依存がない。

$`Y/P`$は係数の比と余りからFP32で近似し、近い整数$`q`$を選ぶ。法は49個以下で、各余りは255以下である。この範囲では、比の丸めと加算による絶対誤差は0.1未満となる。したがって、厳密な整数の差$`Y-qP`$の絶対値は$`P`$未満に収まる。差の絶対値が$`P/2`$より大きい場合、一度だけ$`P`$を加減して符号付きの結果を確定する。FP32は候補の選択に使い、出力値の復元と最終丸めは整数演算で行う。

行列積は複数のSIMDグループでタイルを分担する。行、列、内積の範囲がタイル全体を覆う場合は、コンパイル時に決まるテンソルの寸法を使う。行列の端では実際の寸法を使う。

内積全体が一回の整数精度の範囲に収まる場合、部分内積の配列と加算を省いたパイプラインを使う。長い内積では、最後の剰余の取得と出力の書き込みを同じ反復で行う。

指数の取得と同時に、各行または列の最下位の非ゼロのビットも調べる。整数化した全要素が256の倍数であることを確定できる場合、その情報を保存する。法256のブロック積では、片方の入力ブロックの余りがすべてゼロと確定していれば、行列積を省いてゼロを書き込む。

大きな行列では、行列を四つのブロックに分け、8個のブロック積を7個で求めるStrassen法を一段適用する。ブロックの和と差も法ごとの整数演算で行うため、整数化と最終丸めの定義は変わらない。MとNが1024以上、Mが偶数、Nが128の倍数、Kが2048の倍数で、行のまとまりが128行以上の場合に使う。上下の行を同じ数だけまとめ、保持する行数が指定値を超えないようにする。出力の四つのブロックは専用のカーネルで組み立て、CRTへ渡す。

CRTのパイプラインは整数配列の容量ごとに作成する。必要な桁数を保持できる容量を選び、不要な上位桁をGPUの各スレッドへ持ち込まない。

入力変換では、法ごとに除算用の係数を一度作成する。余りは乗算の上位32ビットと一回の補正から求める。仮数の切り捨ては法の数にかかわらず一度だけ行う。仮数の上位と下位に掛ける2のべき乗の余りは、一つの表から取得する。Bの指数の取得では、隣接するスレッドが隣接する列を読み、複数のSIMDグループで内積方向を分担する。

復元と入力変換の係数は、内積の長さと両入力の整数幅が同じ場合に再利用する。入力の値は毎回GPUで変換する。

$`B`$の行列積用の入力は一度生成して保持する。$`A`$と出力は行のまとまりごとに処理する。Strassen法の入力は、FP64からの整数化とブロックの和と差を同じカーネルで求め、中間の余りの行列を保存しない。入力の64ビットは二つの32ビット整数として読む。CPUは定数の作成と実行指示を担当し、出力を読む前にGPUの完了を待つ。

## 実行環境と資源

Apple Silicon、macOS 26以降、Metal Shading Language 4をコンパイルできるXcode、CMakeが必要である。CPU側の実装にはC11とObjective-CのARCを使う。GPUカーネルはMetal Shading Languageで記述する。検証にはPython 3とC++コンパイラーを使う。外部の数値計算ライブラリーは実装に必要ない。性能比較にはmacOSのAccelerateを使う。

行列の各次元はMetalのテンソルが表現できる符号付き32ビット整数の範囲とする。作業領域は使用する法の数と行列の形状から確保する。失敗は戻り値で分類し、診断メッセージを返す。資源不足やMetalの実行失敗をCPU計算へ置き換える処理は行わない。

## ビルドと検証

XcodeのMetal Toolchainが未導入の場合、先にAppleの追加コンポーネントを導入する。

```sh
xcodebuild -downloadComponent MetalToolchain
```

次のコマンドでライブラリー、Metalカーネル、実験用コマンドをビルドする。

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
```

検証ではPython標準ライブラリーの`Fraction`と任意長整数を使う。入力の整数化、厳密な内積、FP64への最終丸めを独立に計算し、GPUの出力の全ビットと比較する。通常値の丸め、非正規化数、オーバーフロー、桁の打ち消し、INT32の内積の分割を検証する。Cからは同じ計算器で寸法、入力、整数幅を変えた積と失敗時の診断を検証する。C++からもヘッダーを読み込み、ライブラリーをリンクして積を検証する。

ライブラリーとコマンドだけをビルドする場合は、CMakeに`-DBUILD_TESTING=OFF`を指定する。この構成ではC++コンパイラーとPythonを使わない。

## コマンドの使用方法

正方行列について、Accelerateの`cblas_dgemm`とAppleSilicon-FP64の性能を比較する。引数は行列の次数、測定の試行回数、両入力の整数幅の順である。

```sh
./build/fp64_metal benchmark 512 5 60
```

初期化と方式ごとの一回の準備実行を、反復測定から除く。全試行で入力変換を行う。全体の時間は作業領域と出力の確保、入力のコピー、同期を含む。GPUは呼び出し側へ返す出力の記憶領域へ直接書き込む。処理時間には中央値と最小値、最大値を示す。方式の実行順序は試行ごとに巡回させる。

入力変換、行列積、復元の時間はGPUの実行時間である。CPUの待ち時間はGPUの実行時間と重なるため、内訳の合計は全体の実時間と一致しない。`Accelerateとの最大絶対差`は性能測定で使った入力についての差であり、精度の保証ではない。

任意の行列は、行優先のFP64値を並べたバイナリーファイルで入力する。ファイルには見出しを付けない。各要素はリトルエンディアンのIEEE 754 binary64形式である。引数は$`M,N,K`$、$`p_A,p_B`$、二つの入力ファイル、出力ファイルの順である。最後の引数で行のまとまりの大きさを指定できる。

```sh
./build/fp64_metal multiply 128 96 64 60 60 A.bin B.bin C.bin 256
```

ファイルの長さが寸法と一致しない場合や、NaNまたは無限大を含む場合、コマンドは理由を標準エラー出力へ書き、終了コード1で終了する。計算が正常に完了するまで、出力ファイルは開かない。

コマンドのファイルの読み込みと有限値の検査はCPUで行う。ライブラリーでは、有限値の前提に従う入力を受け取り、行列の値をCPUで走査せずに計算する。

### 考察

#### 行列の大きさと比較結果

測定した条件では、小さい行列はAccelerateの方が速い。4096次では両方式の測定範囲が重なり、測定組ごとの速度比も1の前後に変わる。この差では、AppleSilicon-FP64がAccelerateより速いとは判断できない。

次数を2倍にすると、通常の正方行列積の演算量は8倍になる。2048次から4096次への全体の実時間の増加は、AppleSilicon-FP64が約7.18倍、Accelerateが約7.97倍である。この範囲では、AppleSilicon-FP64の仕事量当たりの時間が改善している。ただし、次数によって法の個数と選ばれる計算方法も変わる。速度比の増加だけから、さらに大きい行列でAppleSilicon-FP64が上回るとは予測できない。

測定した2048次と4096次では、「GPUでの計算」に示すStrassen法が選ばれる。1024次と2048次の比較では、行列の寸法とStrassen法の使用有無が同時に変わる。Strassen法単体の高速化率を判断するには、同じ寸法でStrassen法を使う場合と使わない場合を比較する必要がある。

Accelerate側は、出力配列を呼び出し前に確保している。AppleSilicon-FP64は「コマンドの使用方法」に示す処理を含むため、表は既存のAPIを呼び出す場合の全体の実時間の比較である。表は計算器を再利用する場合の性能を示す。計算器を毎回生成する使い方では、初期化の費用が処理時間に加わる。

#### 小さい行列での実行指示と同期

128次では、GPUの各処理時間の代表値の合計は、全体の実時間の代表値の約11%である。GPUの演算時間だけを短縮しても、全体の時間を同じ比率で短縮できるとは限らない。

全体の実時間には、CPUによる実行指示とGPUの実行待ちも含まれる。小さい行列では、演算の仕事量に対して、そうした費用の割合が大きいと考えられる。ただし、各処理の代表値は同一試行の時間ではない。全体の代表値との差を、そのままCPUの処理時間とみなすことはできない。小さい行列の改善では、演算の効率に加えて、実行指示と同期の費用を調べることが重要である。

#### 大きい行列での改善効果

4096次では、余りの行列積がGPUの各処理時間の代表値の合計の約91%を占める。全体の実時間の代表値に対しても約88%を占める。この方式の性能は、必要な法すべての行列積を処理する効率に強く依存する。

次の表は、4096次で一つの処理時間を半減できた場合の改善効果の試算である。全体の代表値から、対象の処理時間の代表値の半分を引いて計算した。表の倍率は、AppleSilicon-FP64の全体の実時間の代表値を、試算した実時間で割った値である。CPUとGPUの処理の重なりは変わらないと仮定する。削減したGPU時間が、そのまま全体の実時間にも反映されると仮定する。

| 半減する処理 | 全体の実時間の試算（ms） | 全体の速度向上の試算 |
|---|---:|---:|
| 入力変換 | 187.2 | 約1.02倍 |
| GPUの行列積 | 106.6 | 約1.79倍 |
| 復元 | 185.9 | 約1.03倍 |

大きい行列では、行列積の効率改善を優先することで、全体の時間を大きく短縮できる余地がある。実際の改善効果は、実装を変更したうえで再計測する必要がある。実行時間の内訳からは、演算能力とメモリー帯域のどちらが行列積を制限しているかまでは分からない。

#### メモリー使用量と整数幅

2048次から4096次へのMetalの作業領域の増加は約3.83倍である。行列を大きくする際は、必要なバッファーの容量も見積もる必要がある。

B側の中間配列に必要な容量は、Bの全体の寸法で決まる。FP64の入力と出力のバッファーにも、行列全体を保持する容量が必要である。そのため、行のまとまりを小さくしても、全体の容量は同じ比率では減らない。行のまとまりを変えると、Strassen法の選択条件にも影響する。保持する行数を減らした場合の処理時間と容量は、両方を測定して判断する必要がある。

「GPUでの計算」で決める法の個数が増えると、行列積の回数と中間配列の容量も増える。整数幅の選択では、用途が必要とする精度と処理量の両方を考慮する必要がある。

#### 精度と測定範囲

同じ入力で試行を反復しても、精度を確認する入力の種類は増えない。反復は、処理時間のばらつきを把握するためのものである。桁の打ち消しによって結果がゼロに近づくと、絶対差が小さくても相対誤差が大きくなりうる。最大絶対差の小ささだけから、広い指数分布や強い桁の打ち消しを持つ入力でも十分な精度があるとは判断できない。

一般の入力では、整数化による切り捨てと、内積の丸め方の違いがAccelerateとの差の要因となりうる。整数化の数値的な意味は「計算の定義」で定める。精度の検証には、「ビルドと検証」で説明する厳密な参照値との比較を使う。

表は、測定条件に記載した環境での実測値である。別のGPUや入力での性能は、それぞれの条件で測定する必要がある。

## CとC++からの使用方法

公開する型、入出力の条件、所有権と失敗時の動作は`include/apple_fp64/matmul.h`で定義する。ヘッダーはC++で読み込む場合に`extern "C"`を適用する。ライブラリーを利用するためのC++のラッパーは必要ない。

`apple_fp64_multiplier_t`はMetalのパイプラインと作業領域を保持するため、複数の積について同じ計算器を再利用できる。作業領域の容量が不足する場合だけ、より大きい領域を確保する。

次の例はCとC++の両方でコンパイルできる。

```c
#include <apple_fp64/matmul.h>
#include <stdio.h>

int main(void)
{
    const double a[] = {1, 2, 3, 4};
    const double b[] = {5, 6, 7, 8};
    apple_fp64_multiplier_t *multiplier = NULL;
    apple_fp64_result_t result = {0};
    apple_fp64_error_t error = {0};
    apple_fp64_status_t status = apple_fp64_multiplier_create("build/fp64.metallib", &multiplier, &error);
    if (status == APPLE_FP64_SUCCESS) {
        status = apple_fp64_multiply(multiplier, a, 4, b, 4, 2, 2, 2,
                                     apple_fp64_default_options(), &result, &error);
    }
    if (status == APPLE_FP64_SUCCESS) {
        printf("%g %g %g %g\n", result.values[0], result.values[1], result.values[2], result.values[3]);
    } else {
        fprintf(stderr, "%s\n", error.message != NULL ? error.message : "CPUのメモリーを確保できません。");
    }
    apple_fp64_result_destroy(&result);
    apple_fp64_error_destroy(&error);
    apple_fp64_multiplier_destroy(multiplier);
    return status == APPLE_FP64_SUCCESS ? 0 : 1;
}
```

CMakeの`apple_fp64`ターゲットをリンクする。実行時には、ビルドで生成された`fp64.metallib`も配置する。

## 参考資料

数値計算の背景は[尾崎スキームIIの原論文](https://arxiv.org/abs/2504.08009)にある。整数によるCRT復元とFP64のビット列の組み立ては、Apple Silicon向けの構成である。Metalでの行列積には[AppleのMetal 4の解説](https://developer.apple.com/documentation/metal/running-inline-ml-operations-in-a-shader-with-metal-4)と、Xcode SDKの`MPPTensorOpsMatMul2d.h`で定義された整数型の組み合わせを使う。
