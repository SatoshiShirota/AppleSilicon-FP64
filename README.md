# AppleSilicon-FP64

日本語 | [English](README.en.md)

Apple SiliconのMetalで、FP64形式の実数密行列積を計算するライブラリーと実験用コマンドである。公開APIとコマンドはC、Metalの資源管理と実行指示はObjective-Cで実装する。C++からも同じCのヘッダーと関数を利用できる。入力の値に応じて、整数剰余による行列積と、整数演算によるFP64の積和演算を選ぶ。値に依存する数値演算はすべてGPUで実行する。

## 用語

| 用語 | この文書での意味 |
|---|---|
| 法 | 整数の余りを求めるときの除数。 |
| CRT | 中国剰余定理による復元。複数の法に対する余りから、範囲内の整数を一意に求める。 |
| 整数幅 | 行または列の最大値を基準として、損失なく整数化するための二進数の桁数。FP64の仮数の桁数とは異なる。 |

## 計算の定義

入力はFP64の値を持つ、行優先の連続した行列$`A`$と$`B`$である。全有限値、非正規化数、符号付きゼロ、NaN、無限大を扱う。空の行列と$`K=0`$を許容する。係数付きの積と転置を含むBLAS互換の操作は扱わない。

行列$`A`$の行ごとに$`h_i=1+\lfloor\log_2\max_k|A_{ik}|\rfloor`$、行列$`B`$の列ごとに同じ定義で$`g_j`$を決める。全要素がゼロの場合の指数は0とする。指数の取得にはFP64のビット列を使う。解析ではNaNと無限大を除く。

有限の非ゼロ値について、最下位の非ゼロビットの指数を行ごとに$`\ell_i`$、列ごとに$`t_j`$とする。全要素がゼロの場合の必要な幅は1とする。入力を損失なく保持できる整数幅を次の式で決める。

$$
p_A=\max_i\max(1,h_i-\ell_i),\qquad
p_B=\max_j\max(1,g_j-t_j)
$$

入力がすべて有限であれば、元の入力の整数幅と内積の長さを、利用可能な法の積で保持できるか調べる。保持できない場合は、内積方向の指数を調整して整数幅を求め直す。

調整量は、Aの第$`k`$列とBの第$`k`$行の最大絶対値から決める。どちらかの全要素がゼロの場合は$`d_k=0`$とする。それ以外では、次の指数と調整量を使う。

$$
\alpha_k=1+\left\lfloor\log_2\max_i|A_{ik}|\right\rfloor,\qquad
\beta_k=1+\left\lfloor\log_2\max_j|B_{kj}|\right\rfloor
$$

$$
d_k=\left\lfloor\frac{\beta_k-\alpha_k}{2}\right\rfloor,\qquad
\widetilde A_{ik}=A_{ik}2^{d_k},\qquad
\widetilde B_{kj}=B_{kj}2^{-d_k}
$$

各積は$`\widetilde A_{ik}\widetilde B_{kj}=A_{ik}B_{kj}`$を満たす。調整した値に同じ手順を適用し、行と列の指数と整数幅を求める。調整した値をFP64へ丸める処理は行わない。

元の入力または指数を調整した入力で必要な範囲を保持できる場合、INT8の行列積とCRTを使う。整数化による切り捨ては発生しない。出力は厳密な内積をFP64へ最近接偶数丸めした値である。厳密にゼロとなる積は正のゼロになる。

$$
\widehat C_{ij}=\mathrm{RN}_{64}\left(\sum_{k=0}^{K-1} A_{ik}B_{kj}\right)
$$

指数を調整しても必要な整数幅が法の積を超える場合、またはNaNや無限大を含む場合、元の入力を使い、GPUの整数演算でFP64の積和を実行する。内積は$`s_0=+0`$から内積方向の順に求める。各積和では、積と加算を合わせて一度だけ最近接偶数丸めする。

$$
s_{k+1}=\mathrm{RN}_{64}(A_{ik}B_{kj}+s_k),\qquad
\widehat C_{ij}=s_K
$$

どちらの計算方法でも、非正規化数はFP64の刻みに直接丸める。オーバーフローは符号付きの無限大となる。非ゼロの負の値が丸めによってゼロとなる場合は負のゼロになる。NaNを含む積和、ゼロと無限大の積、逆符号の無限大の加算は、ビット列`0x7ff8000000000000`の静かなNaNを返す。NaNのペイロードとCPUの浮動小数点例外フラグは伝播しない。

計算方法によって丸めの回数と順序が異なる。`cblas_dgemm`とのビット単位の一致や、すべての入力に対する厳密な内積の最終丸めは保証しない。入力の指数が広い場合も、入力値を事前に切り捨てることはない。

## GPUでの計算

GPUで使う演算を次の表に示す。

| 演算 | 実行の方法 |
|---|---|
| 入力の解析 | FP64のビット列から指数と最下位ビットを調べ、必要な整数幅と非有限値の有無を求める。 |
| INT8の余りへの変換 | 仮数と指数から整数化した値の余りを求める。 |
| INT8入力・INT32蓄積による行列積 | Metalの`mpp::tensor_ops::matmul2d`を使う。 |
| CRTとFP64形式への丸め | 整数配列から結果のビット列を組み立てる。 |
| FP64の積和演算 | 仮数の積と加数を整数で保持し、加算後にFP64のビット列へ丸める。 |

Aの行とBの列の解析は、同じMetalの計算エンコーダーに記録して並行に実行する。両方の解析が完了し、メモリーへの書き込みが後続の処理へ見えるように同期してから、整数幅と非有限値の有無を集計する。

指数調整が必要な場合は、同じ解析用のバッファーにAの列とBの行の解析結果を格納し、GPUで調整量を求める。調整量の算出が完了してから、行と列の解析結果を調整後の指数で更新する。調整量の算出と再解析は、一回の追加のMetalの実行指示にまとめる。入力のビット列は保持し、解析と余りへの変換で整数の指数を加減する。Strassen法でも、各ブロックに対応する内積方向の調整量を使う。

### 整数剰余による行列積

法には256以下の互いに素な整数を大きい順に使う。合成数によって複数の素因数を一つの行列積で扱う。法の積$`P`$が$`P>2K2^{p_A+p_B}`$を満たすまで法を選ぶ。計算方法の選択と丸めの意味は「計算の定義」で定める。

余りは符号付きINT8に収める。内積は各部分の絶対値の総和が$`2^{24}`$以下になる長さに分割する。この範囲では、FP32の中間値を使う実行でも整数を正確に表せる。部分内積はINT32でまとめて加算し、オーバーフローしない長さごとに余りを求める。INT32の出力型だけを根拠に、長い内積全体の整数精度を仮定しない。整数化の指数は分割によって変えない。

CRTでは、各法について$`W_t=(P/m_t)((P/m_t)^{-1}\bmod m_t)`$を作成する。各出力の余りを$`r_t`$とすると、$`Y=\sum_t r_t W_t`$を基数$`2^{18}`$の整数配列で求める。各桁の積の総和と繰り上がりは32ビット符号なし整数に収まる。桁ごとの総和には、他の桁への依存がない。

$`Y/P`$は係数の比と余りからFP32で近似し、近い整数$`q`$を選ぶ。法は49個以下で、各余りは255以下である。この範囲では、比の丸めと加算による絶対誤差は0.1未満となる。したがって、厳密な整数の差$`Y-qP`$の絶対値は$`P`$未満に収まる。差の絶対値が$`P/2`$より大きい場合、一度だけ$`P`$を加減して符号付きの結果を確定する。FP32は候補の選択に使い、出力値の復元と最終丸めは整数演算で行う。

行列積は複数のSIMDグループでタイルを分担する。行、列、内積の範囲がタイル全体を覆う場合は、コンパイル時に決まるテンソルの寸法を使う。行列の端では実際の寸法を使う。

内積全体が一回の整数精度の範囲に収まる場合、部分内積の配列と加算を省いたパイプラインを使う。長い内積では、最後の剰余の取得と出力の書き込みを同じ反復で行う。

整数化した全要素に共通する下位ゼロビット数の下限は、入力の解析結果と決定した整数幅から求める。法256のブロック積では、AとBのそれぞれについて、対象となる行または列の下限の最小値を求める。二つの最小値の合計が8以上なら、内積の各項が256の倍数となるため、行列積を省いてゼロを書き込む。Strassen法では、和と差を作る両方のブロックを含めて最小値を求める。

整数剰余による大きな行列積では、行列を四つのブロックに分け、8個のブロック積を7個で求めるStrassen法を一段適用する。ブロックの和と差も法ごとの整数演算で行うため、整数化と最終丸めの定義は変わらない。MとNが1024以上、Mが偶数、Nが128の倍数、Kが2048の倍数で、行のまとまりが128行以上の場合に使う。上下の行を同じ数だけまとめ、保持する行数が指定値を超えないようにする。出力の四つのブロックは専用のカーネルで組み立て、CRTへ渡す。

CRTのパイプラインは整数配列の容量ごとに作成する。必要な桁数を保持できる容量を選び、不要な上位桁をGPUの各スレッドへ持ち込まない。

入力変換では、法ごとに除算用の係数を一度作成する。余りは乗算の上位32ビットと一回の補正から求める。仮数と指数への分解は、法の数にかかわらず一度だけ行う。入力の下位ビットを右へずらす場合、失われるビットはすべてゼロである。仮数の上位と下位に掛ける2のべき乗の余りは、一つの表から取得する。Bの指数の取得では、隣接するスレッドが隣接する列を読み、複数のSIMDグループで内積方向を分担する。

復元と入力変換の係数は、内積の長さと両入力の整数幅が同じ場合に再利用する。入力の値は毎回GPUで変換する。

$`B`$の行列積用の入力は一度生成して保持する。$`A`$と出力は行のまとまりごとに処理する。Strassen法の入力は、FP64からの整数化とブロックの和と差を同じカーネルで求め、中間の余りの行列を保存しない。

### 整数演算によるFP64の積和演算

FP64の仮数同士の積を、最大106ビットの整数として求める。加数と指数を揃え、128ビットの整数で加算または減算する。整数の範囲より下へ移動する桁は、非ゼロのビットがあるかを最下位ビットへ集約する。この情報を最終丸めに使い、丸めの前に積だけをFP64へ変換することはない。

積と加数の符号が同じ場合は加算し、異なる場合は減算する。減算では、最上位桁からの借りによって結果の符号を決める。借りをビットマスクへ展開し、符号による分岐を使わずに差の絶対値を求める。加算と減算の両方で、同じ最終丸めの処理を使う。

仮数の乗算は32ビットの部分積と繰り上がりから直接求める。指数合わせは32ビットと64ビットの移動を分け、配列を可変位置で参照する処理を避ける。最終丸めでは、保持する仮数の直下に二つのビットを残す。一つは中間値を判定するビットで、もう一つはさらに下位の非ゼロの情報を含む。仮数の取り出しと丸めの判定に、同じ指数合わせの結果を使う。丸めで加える0または1はビット演算で求め、繰り上がりは整数の比較から求める。

入力解析で両行列が有限と分かった場合は、有限の入力用にコンパイルしたパイプラインを使う。各積和での乗数のNaNと無限大の判定を省く。積和の途中で発生するオーバーフローと非正規化数の丸めは、入力の範囲にかかわらず処理する。

出力の行と列をスレッドグループで分担する。入力は共有メモリーへ読み込むときに、符号付きの仮数と指数へ分解する。複数の出力で分解済みの値を再利用し、各積和で同じ乗数を分解する処理を省く。内積方向は入力の順序を保つ。最後のまとまりでは、実際に存在する項だけを加算する。余りの行列とCRTの作業領域は使わない。

### CPUによる実行指示

入力の64ビットは二つの32ビット整数として読む。GPUが求めた整数幅と非有限値の有無を、解析一回につき12バイトの結果としてCPUが受け取る。CPUは解析結果から計算パイプラインと作業領域を選ぶ。CRTを使う場合、入力の値に依存しない復元係数を作成する。行列の値をCPUで走査したり、CPUで内積を求めたりすることはない。出力を読む前にGPUの完了を待つ。

## 実行環境と資源

Apple Silicon、macOS 26以降、Metal Shading Language 4をコンパイルできるXcode、CMakeが必要である。CMakeの最低バージョンは[CMakeLists.txt](CMakeLists.txt)の`cmake_minimum_required`で定める。CPU側の実装にはC11とObjective-CのARCを使う。GPUカーネルはMetal Shading Languageで記述する。検証にはPython 3とC++コンパイラーを使う。外部の数値計算ライブラリーは実装に必要ない。性能比較にはmacOSのAccelerateを使う。

行列の各次元はMetalのテンソルが表現できる符号付き32ビット整数の範囲とする。入力と出力、行と列の解析結果は行列全体について保持する。指数調整では、内積の項数と同じ個数の32ビット整数を追加で保持する。解析用の配列は、入力の行と列の両方を扱える容量まで拡張して再利用する。CRTの中間配列の容量は、使用する法の数と行のまとまりの大きさから決まる。FP64の積和演算では、行のまとまりの設定によって作業領域は変わらない。失敗は戻り値で分類し、診断メッセージを返す。資源不足やMetalの実行失敗をCPU計算へ置き換える処理は行わない。

## ビルドと検証

XcodeのMetal Toolchainが未導入の場合、先にAppleの追加コンポーネントを導入する。

```sh
xcodebuild -downloadComponent MetalToolchain
```

次のコマンドでライブラリー、Metalカーネル、実験用コマンドをビルドする。

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
```

検証ではPython標準ライブラリーの`Fraction`を使う。CRTを使う入力では、指数調整の有無にかかわらず、厳密な内積と最終丸めを独立に計算する。指数調整後もCRTの範囲を超える入力と、非有限値を含む入力では、各積和の厳密な有理数をFP64へ丸める。GPUの出力の全ビットを期待値と比較する。通常値の丸め、非正規化数、オーバーフロー、桁の打ち消し、NaN、無限大、INT32の内積の分割を検証する。行と列で下位ゼロビット数が異なる入力も検証する。

指数調整では、積和ごとの丸めで失われる項と、FP64の範囲を超える積の打ち消しを検証する。調整した値の絶対値がFP64の最小の正の非正規化数より小さくなる場合にも、入力の情報と最終出力のゼロの符号を保つことを確認する。

整数演算によるFP64の積和演算は、全指数範囲と桁の打ち消しを含む2万件について、CPUの`fma`と比較する。Cからは同じ計算器で寸法と入力の範囲を変えた積、失敗時の診断を検証する。Strassen法では、上下と左右のブロックで下位ゼロビット数が異なる長方形の積を、厳密な整数の期待値と比較する。内積方向の指数が異なるブロックについても、同じ積を検証する。C++からもヘッダーを読み込み、ライブラリーをリンクして積を検証する。

ベンチマークでは、区間の実行順序を検証する。出力された区間の値から時間、速度比、絶対偏差を独立に集計し、表示された集計値と照合する。

ライブラリーの導入は、独立したCとC++のプロジェクトから検証する。ソースを組み込む場合と、インストール先を移動したパッケージを使う場合の両方で、公開ヘッダーの読み込み、リンク、Metalファイルの取得と行列積を確認する。ソースを組み込む場合は、親の`BUILD_TESTING`が有効でも本ライブラリーのコマンドとテストが追加されないことを確認する。

ライブラリーとコマンドだけをビルドする場合は、CMakeに`-DBUILD_TESTING=OFF`を指定する。この構成ではC++コンパイラーとPythonを使わない。

ライブラリーだけをビルドする場合は、さらに`-DAPPLE_FP64_BUILD_TOOLS=OFF`を指定する。`APPLE_FP64_BUILD_TOOLS`は単独ビルドで既定が`ON`、他のプロジェクトへ組み込む場合は既定が`OFF`となる。テストは単独ビルドで`BUILD_TESTING`が有効な場合に構築する。テストに必要なコマンドも、この場合は構築する。

## コマンドの使用方法

正方行列について、Accelerateの`cblas_dgemm`とAppleSilicon-FP64の性能を比較する。引数は行列の次数、測定の試行回数の順である。

```sh
./build/fp64_metal benchmark 512 5
```

初期化と準備実行を、反復測定から除く。準備実行は方式を交互に切り替え、各方式の累計が0.25秒以上、かつ各方式を2区間以上実行するまで行う。各区間では同じ入力の積を連続して求める。準備実行の直近の時間から、一区間が約0.05秒となる反復回数を方式ごとに求める。積を一回求める時間が長い場合は、一回とする。準備実行の終了後は反復回数を固定し、測定値に応じて変更しない。

一試行では、両方式を二回ずつ測定する。実行する区間の順序を次の表に示す。

| 試行 | 第一区間 | 第二区間 | 第三区間 | 第四区間 |
|---|---|---|---|---|
| 奇数回 | Accelerate | AppleSilicon-FP64 | AppleSilicon-FP64 | Accelerate |
| 偶数回 | AppleSilicon-FP64 | Accelerate | Accelerate | AppleSilicon-FP64 |

両方式とも、呼び出し側の単調な時計で区間全体を測る。反復回数で割り、行列積一回当たりの実時間を求める。AppleSilicon-FP64では、各反復の戻り値を解放する時間も含める。全反復で入力の解析と変換を行う。作業領域と出力の確保、入力のコピー、同期も時間に含む。Accelerateは、あらかじめ確保した出力配列を再利用する。GPUは呼び出し側へ返す出力の記憶領域へ直接書き込む。

各試行では、方式ごとに二つの区間の平均を求める。同じ試行のAccelerateの平均をAppleSilicon-FP64の平均で割り、その試行の速度比とする。方式ごとの時間と試行ごとの速度比には、中央値と最小値、最大値を示す。方式ごとの時間には、中央値からの絶対偏差の中央値を、時間の中央値で割った百分率も示す。区間ごとの値と実行順序を出力し、外れ値は除外しない。

入力変換の時間は、入力の解析も含むGPUの実行時間である。行列積と復元の時間もGPUの実行時間である。CPUの待ち時間はGPUの実行時間と重なるため、内訳の合計は全体の実時間と一致しない。`Accelerateとの最大絶対差`は性能測定で使った入力についての差であり、精度の保証ではない。

任意の行列は、行優先のFP64値を並べたバイナリーファイルで入力する。ファイルには見出しを付けない。各要素はリトルエンディアンのIEEE 754 binary64形式である。引数は$`M,N,K`$、二つの入力ファイル、出力ファイルの順である。最後の引数で行のまとまりの大きさを指定できる。

```sh
./build/fp64_metal multiply 128 96 64 A.bin B.bin C.bin 256
```

ファイルの長さが寸法と一致しない場合、コマンドは理由を標準エラー出力へ書き、終了コード1で終了する。計算が正常に完了するまで、出力ファイルは開かない。

コマンドのファイルの読み込みはCPUで行う。NaNと無限大も入力できる。数値の扱いは「計算の定義」で定める。

## 計測結果と性能

### 考察

#### 行列の大きさと比較結果

通常入力の測定では、2048次までの行列は全21試行でAccelerateの方が速い。4096次と8192次では、全21試行でAppleSilicon-FP64の方が速い。

次数を2倍にすると、通常の正方行列積の演算量は8倍になる。2048次から4096次へのAppleSilicon-FP64の全体の実時間の増加は約6.94倍、4096次から8192次では約7.71倍である。測定した2048次以上では「整数剰余による行列積」に示すStrassen法を使う。ただし、寸法によって法の個数も変わるため、異なる寸法の測定からStrassen法単体の高速化率を求めることはできない。

表は、計算器を再利用してAPIを呼び出す場合の全体の実時間を比較する。計算器を毎回生成する場合、初期化の費用も加わる。Accelerateは確保済みの出力配列を使うため、両APIが必要とする処理は異なる。計測に含める処理は「コマンドの使用方法」で定める。

#### 入力の解析と小さい行列

損失のない整数幅を決めるため、入力をGPUで解析し、CPUが解析結果を受け取ってから計算方式を選ぶ。APIを呼び出すたびに、この同期が発生する。入力の解析を省くと、同じ計算器に異なる指数範囲の行列を渡した場合に、小さい項を失うおそれがある。

128次では、GPUの各処理時間の代表値の合計は全体の実時間の代表値の約19%である。演算量が小さい場合、実行指示、同期、出力の確保の費用が大きいと考えられる。ただし、各代表値は同一試行の値ではないため、全体との差をCPUの時間として扱うことはできない。

#### 大きい行列の処理とメモリー

8192次では、余りの行列積がGPUの各処理時間の代表値の合計の約94%を占める。大きい行列の速度は、必要な法の行列積を処理する効率に強く依存する。入力から整数幅を決めるため、必要な法の個数は入力の値によって変わる。

4096次から8192次へのMetalの作業領域の増加は約3.84倍である。入力と出力のFP64バッファー、Bの中間配列は行列全体について必要になる。そのため、行のまとまりを小さくしても全体の容量は同じ比率では減らない。行のまとまりを変えるとStrassen法の使用条件にも影響する。時間と容量の両方を測って判断する必要がある。

#### 精度と測定範囲

測定した通常入力と、内積方向で指数が相殺される入力ではCRTを使い、整数化による切り捨ては発生しない。Accelerateとの差は、内積の丸めの順序と回数が異なることから生じる。同じ入力の反復測定は、精度を確認する入力の種類を増やさない。数値検証は「ビルドと検証」で説明する独立した参照値との比較で行う。

指数調整後もCRTの範囲を超える入力では、FP64の積和演算による計算を使う。この計算は各積和で丸めるため、桁の打ち消しによって相対誤差が大きくなる場合がある。通常入力での絶対差の小ささを、広い指数範囲における精度の保証として使うことはできない。計算の数値的な意味は「計算の定義」で定める。

#### 広い指数範囲での性能

性能は、入力全体の指数範囲だけでは決まらない。内積方向でAとBの指数の変化が相殺される場合、損失なく整数化できる幅まで調整することで、INT8の行列積とCRTを使える。測定した入力では、通常入力と同じ個数の法を使い、大きい行列の処理時間も通常入力に近い。

指数が相殺される4096次と8192次では、同じ試行の速度比の中央値でAppleSilicon-FP64がAccelerateより約1.09～1.14倍速い。ただし、8192次の正負が混在する入力では、一部の試行でAccelerateより遅い値も観測した。中央値だけでなく、表に示す範囲も性能の見積もりに使う必要がある。

指数調整には、入力の追加の解析と、CPUが解析結果を受け取るための同期が必要になる。小さい行列では、演算量に対してこの費用の割合が大きい。調整してもCRTの範囲に収まらない入力では、解析の費用をかけたうえでFP64の積和演算を行うため、指数調整による高速化は得られない。

CRTを使う場合は、余りの行列と復元用の作業領域が必要になる。指数調整用の配列の容量だけで、広い指数範囲の入力のメモリー使用量を見積もることはできない。計算方法と、入力から求まる法の個数を合わせて確認する必要がある。

測定結果は、記載した環境と入力についての値である。別のGPUや入力の性能は、それぞれの条件で測定する必要がある。

## CとC++からの使用方法

公開する型、入出力の条件、所有権と失敗時の動作は`include/apple_fp64/matmul.h`で定義する。ヘッダーはC++で読み込む場合に`extern "C"`を適用する。ライブラリーを利用するためのC++のラッパーは必要ない。

Doxygenコメントには日本語と英語の説明を含める。[Doxygenの言語切り替え](https://www.doxygen.nl/manual/commands.html#cmdtilde)を使い、`OUTPUT_LANGUAGE`を`Japanese`または`English`に設定すると、選んだ言語の説明を出力できる。

`apple_fp64_multiplier_t`はMetalのパイプラインと作業領域を保持するため、複数の積について同じ計算器を再利用できる。作業領域の容量が不足する場合だけ、より大きい領域を確保する。

次の例はCとC++の両方でコンパイルできる。

```c
#include <apple_fp64/matmul.h>
#include <stdio.h>

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "使用方法: %s /path/to/fp64.metallib\n", argv[0]);
        return 1;
    }
    const double a[] = {1, 2, 3, 4};
    const double b[] = {5, 6, 7, 8};
    apple_fp64_multiplier_t *multiplier = NULL;
    apple_fp64_result_t result = {0};
    apple_fp64_error_t error = {0};
    apple_fp64_status_t status = apple_fp64_multiplier_create(argv[1], &multiplier, &error);
    if (status == APPLE_FP64_SUCCESS) {
        status = apple_fp64_multiply(multiplier, a, 4, b, 4, 2, 2, 2,
                                     apple_fp64_default_options(), &result, &error);
    }
    if (status == APPLE_FP64_SUCCESS) {
        printf("%g %g %g %g\n", result.values[0], result.values[1], result.values[2], result.values[3]);
    } else {
        fprintf(stderr, "%s\n", error.message != NULL ? error.message : "CPUのメモリーを確保できません。");
    }
    apple_fp64_result_destroy(&result);
    apple_fp64_error_destroy(&error);
    apple_fp64_multiplier_destroy(multiplier);
    return status == APPLE_FP64_SUCCESS ? 0 : 1;
}
```

### ソースから組み込む

利用側の`CMakeLists.txt`に、ソースのディレクトリーを追加する。

```cmake
add_subdirectory(path/to/AppleSilicon-FP64 apple-fp64)
```

この利用方法では、ライブラリーと必要なMetalカーネルだけを既定でビルドする。利用側がC++コンパイラーやPythonを用意する必要はない。C++で書いた利用側のプログラムには、C++コンパイラーが必要である。

### インストールして利用する

「ビルドと検証」の手順で生成したライブラリーを、指定したディレクトリーへインストールする。

```sh
cmake --install build --prefix /path/to/apple-fp64
```

インストールには、静的ライブラリー、公開ヘッダー、Metalファイル、CMakeのパッケージ設定とLICENSEが含まれる。実験用コマンドとテストはインストールしない。

利用側の`CMakeLists.txt`でパッケージを検索する。

```cmake
find_package(AppleSiliconFP64 CONFIG REQUIRED)
```

利用側の構成時に、インストール先を検索パスへ追加する。

```sh
cmake -S . -B build -DCMAKE_PREFIX_PATH=/path/to/apple-fp64
```

インストール先のディレクトリー全体を移動しても利用できる。移動した場合は、移動先を検索パスへ指定する。

### リンクとMetalファイルの配置

どちらの導入方法でも、`AppleSiliconFP64::apple_fp64`をリンクする。公開ヘッダーの検索パスと、MetalおよびFoundationのリンク設定は、このターゲットから利用側へ伝わる。`AppleSiliconFP64_METALLIB`には、対応する`fp64.metallib`の絶対パスが入る。ソースを組み込んだ場合のファイルは、ビルド時に生成される。

コマンドラインアプリケーションでは、次の例でMetalファイルを実行ファイルと同じディレクトリーへ配置できる。

```cmake
add_executable(my_app main.c)
target_link_libraries(my_app PRIVATE AppleSiliconFP64::apple_fp64)
add_custom_command(TARGET my_app POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_if_different
        "${AppleSiliconFP64_METALLIB}"
        "$<TARGET_FILE_DIR:my_app>/fp64.metallib"
    VERBATIM)
```

macOSのアプリケーションでは、Metalファイルをアプリケーションバンドルの資源として同梱する。実行時に配置先のパスを取得し、`apple_fp64_multiplier_create`へ渡す。ライブラリーはファイルを自動で検索しない。実行時の作業ディレクトリーに依存しないパスを指定する。
